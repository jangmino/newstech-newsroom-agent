공급자 한도·동시성·결제·Cloud Run 자원·비밀키 설정은 유지했다.
아래 미완료 항목을 실측하고 상향 여부를 사용자와 함께 결정한다.

30명이 최초 계획·브리핑·일반 비교를 각각 한 번 하면 최소90회 모델 호출이며 질답은 별도다.
같은 승인 조건은 자료 계산을 공유하지만 Gemini 응답은 공유하지 않는다. A~C 조건이 모두
다르면 공공 API도 최대90회가 될 수 있다. 분당한도·동시성·요청 길이를 따로 봐야 한다.

- [ ] 실제 Gemini 프로젝트의 RPM·TPM·일일한도, KOSIS/OpenDART 승인 한도 확인.
      현재 앱 기본 Gemini 분당30/동시8, 공공자료 분당30/동시2와 비교하되 stage 실설정도 확인한다.
- [x] 새 후보 배포 승인, 롤백 리비전 보존, 후보·공개 주소의 스냅샷 동작 확인.
      현재 `newsroom-stage-investigationb-20261006`, 롤백 `newsroom-stage-newline-20260930`.
- [ ] 30명 동일 질문 / 다섯 사례 혼합 / 서로 다른 수정 질문의 단계별 실제 리허설.
      p50/p95·대기시간·429/503·취소·재시도·캐시 적중·공공 API별 요청 수를 수집한다.
- [ ] 기존 대기120초·전체180초 제한 안에 브리핑이 완료되는지 확인.
      코드는 여전히1프로세스/기존배포 구조이며 다중 인스턴스 전체 한도 제어를 새로 만들지 않았다.
      소규모 최종 혼합 5건은 4.63~7.29초에 반환됐으나 C 브리핑1건은 검증 거부,
      재승인 후5.84초에 복구했다. HTTP200·큐완료 수를 브리핑 성공률로 사용하지 않는다.
- [ ] 모델 출력 검증 거부율과 재승인 복구율 확인. B의 연령 표현 지시는 보완했지만,
      숫자 슬롯·인용 검증을 느슨하게 하거나 자동 재요청으로 오류를 숨기지 않는다.
- [ ] 브리핑 실제 입력/출력 토큰 계측. 현재 E 최대40근거, 나머지24근거, 브리핑 출력4096상한.
      긴 출력과 비용·TPM의 관계를 측정한 뒤 조정한다. 지금 측정은 API 호출수·벽시계 시간 중심이다.
- [ ] 요청 한도·동시성 상향을 검토하고 증거·중단기준을 기록. 잔액/월 결제한도와 RPM은 별개다.
- [x] 공식 저장 원자료10개+manifest의 배포 패키지·해시와 새 후보의 재계산·캐시 재사용 확인.
- [ ] 캐시 TTL/용량·재시작을 포함한 부하 검증 및 신규 다섯 사례의 Gemini 장애용
      사전 생성 브리핑·일반응답 준비 여부 결정.
- [ ] 원자료 검증일(2026-10-05), 정정 공시·통계 잠정치 갱신 필요 확인.
      D/E 임의 회사·연도와 B 경북 외 시군은 행사 중 즉흥 확장하지 않는다.
- [ ] 조별 사례 배분·진행 시간·행사장 네트워크·Windows 내려받기·접근코드·운영 담당 확인.
- [ ] 실습 진행용 예시: E 5개년 구성표 → 같은 보고서 전기 비교 → 분류 차이 → 미확인 원인 → 사람 검토.
      기사 작성·발행 자동화, 시장 전체 CB, 반도체 혼합 인과분석, 자사 파일럿은 제외한다.
