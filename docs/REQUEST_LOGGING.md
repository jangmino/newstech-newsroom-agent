# 요청 ID와 구조화 로그 (M3)

참가자가 오류 화면의 **문의용 요청 번호**를 운영자에게 전달하면, 같은 번호의 서버 로그에서
어느 API가 어떤 상태로 끝났는지 확인합니다. 질문이나 접근코드를 전달할 필요가 없습니다.
[ADR 0013](decisions/0013-request-id-and-safe-logs.md)의 작은 운영 단위입니다.

## 참가자 경험과 확인 방법

- 기존 한국어 오류 안내 뒤에 `문의용 요청 번호: …`를 표시합니다. 분석·조회·입장·입장
  상태 확인의 오류에 적용하며 서버 응답이 없는 연결 실패에는 번호를 만들지 않습니다.
- 입력 수정·재시도·나가기에는 기존 오류와 번호를 함께 지웁니다. 새 실패는 새 번호를
  표시합니다. 자료 오류 뒤 snapshot으로 전환할 때는 기존 정책대로 이전 오류 안내와
  그 오류의 번호를 함께 보존합니다. 현재 snapshot 요청의 번호로 바꾸지 않습니다.
- 입장 거절 시에도 결과·비교·검토를 숨깁니다. 재입장 후 요청을 자동 실행하지 않습니다.
- 자료 선택·조건 승인·계산·사람 검토 규칙은 유지합니다. 요청 번호는 기사 사용 승인이나
  참가자 개인 식별자가 아닙니다.

`make dev-api`를 실행한 터미널에서 JSON 로그의 `request_id`를 검색할 수 있습니다.
오프라인 확인은 실제 조회를 서버에서 꺼 둔 상태에서 화면의 공식 실제 자료 분석을
시도하면 됩니다. 활성화 검사에서 중단되어 외부 공급자를 호출하지 않고 503과 번호를
표시합니다. 실제 조회가 켜진 환경에서는 이 동작이 실제 API 접근으로 이어질 수 있으므로
이번 검증은 프로세스 설정 `LIVE_API_ENABLED=false`, `PUBLIC_DATA_MODE=mock`으로 했습니다.
이후 모의 자료를 선택하고 조건을 분석·승인해 정상 흐름으로 돌아갈 수 있습니다.

## 응답 계약

모든 HTTP 응답에 서버가 생성한 UUID v4 `X-Request-ID`를 추가합니다. 참가자가 같은
이름의 요청 헤더를 보내도 재사용하지 않습니다. 응답 헤더와 로그 ID는 같습니다.
`/plan`, `/execute`, 이전 `/analyze` 성공 본문의 기존 `request_id`도 같은 값입니다.
분석과 실행, 동일 조건 재승인, 원자료 캐시 재사용·동시 요청 공유는 각각 별도 HTTP 요청 ID입니다.
계획·승인 이력을 저장하거나 두 요청을 하나의 세션으로 추적하지 않습니다.

기존 성공/오류 본문의 필드를 유지합니다. 오류의 번호는 헤더에서 읽으며, 프론트엔드는
UUID v4 형식만 표시합니다. 형식이 잘못되거나 헤더가 없으면 번호를 표시하지 않습니다.
허용 출처에 `Access-Control-Expose-Headers: X-Request-ID`를 제공하고, CORS 사전 요청과
접근코드 검사에서 거절된 요청도 ID가 있습니다. 응답 JSON 읽기 실패에도 유효한 헤더가
있으면 문의 번호를 표시합니다. 프록시가 자체 생성한 오류는 번호가 없을 수 있습니다.

예상하지 못한 HTTP 처리 예외는 500과 기존 오류 구조의 `detail.code=internal_error`,
고정 한국어 `message`, 빈 `field_errors`를 반환합니다. 예외 메시지/공급자 원문은 넣지 않습니다.
`no-store`와 허용 출처의 CORS 응답도 유지합니다. 이미 전송이 시작된 응답은 500으로
교체할 수 없으므로 중단으로 기록하고 고정된 안전한 예외만 상위 서버로 전달합니다.

## 로그 계약

`newsroom_agent.requests` 전용 logger가 stdout에 HTTP 요청당 JSON 한 줄을 출력합니다.
루트 logger로 중복 전파하지 않습니다. 파일 저장·로그 조회 API·수집 서비스는 추가하지 않습니다.

| 필드 | 허용 내용 |
|---|---|
| `timestamp` | 로그 기록 시점, UTC ISO 시각 |
| `severity` | 오류 없는 2xx/3xx `INFO`, 오류 코드 또는 취소/중단 `WARNING`, 5xx `ERROR` |
| `event` | 고정값 `http_request` |
| `request_id` | 서버가 새로 만든 UUID v4 |
| `method` | GET/HEAD/POST/PUT/PATCH/DELETE/OPTIONS, 그 외 `OTHER` |
| `route` | 고정된 기존 API·health·문서 경로, `/`, `/assets/*`, 그 외 `other` |
| `status_code` | 전송을 시작한 HTTP 상태 코드, 시작 전 취소 등은 null |
| `duration_ms` | ASGI 경계 진입부터 종료까지 단조 시계로 측정한 밀리초 |
| `outcome` | `completed`, `cancelled`, `interrupted` |
| `error_code` | 허용된 애플리케이션 오류 코드 또는 고정 분류, 성공은 null |

`completed`는 응답 처리가 끝났다는 뜻이며 503도 completed입니다. `status_code`와 함께
읽습니다. 앱이 관찰한 취소는 `request_cancelled`, 불완전한 전송은 `response_interrupted`로
구분합니다. 브라우저에서 요청을 취소해도 서버 처리가 계속되면 로그에는 완료가 남을 수
있습니다. 서버 응답 완료는 참가자가 실제로 결과를 읽었다는 확인이 아닙니다.

접근코드·조건 검증·모델/공공자료 한도·장애·snapshot 오류의 허용된 코드를 기록합니다.
모르는 코드는 `http_error`, 일반 404/405/422는 각각 `not_found`/`method_not_allowed`/
`invalid_request`입니다. HTTP 상태는 있어도 더 구체적인 실패 코드가 없으면 `http_error`입니다.

다음 내용은 로그 필드로 수집하지 않습니다: 질문·조건·응답 본문, 요청/응답 헤더,
접근코드·키, URL 쿼리, IP·사용자 에이전트, 예외 메시지·공급자 원문. 알 수 없는 경로와
메서드를 그대로 출력하지 않으므로 경로·메서드에 넣은 값도 로그에 들어가지 않습니다.
요청·응답 본문을 읽거나 버퍼링해서 오류 코드를 추출하지 않습니다. 예외 처리기가 고정
오류 코드만 전달합니다. 단순 마스킹에 의존하지 않는 허용 목록 방식입니다.

`RequestLoggingMiddleware`는 CORS와 접근 검사 바깥에서 ID·시각을 설정합니다.
Python [ContextVar](https://docs.python.org/3.12/library/contextvars.html)를 사용해 비동기 요청과
동기 계획 작업의 ID를 구분하고 종료 시 복구합니다. 공공자료 캐시 안에는 ID를 넣지 않습니다.
HTTP 밖에서 순수 계획/결과 함수를 직접 호출하면 기존처럼 새 UUID를 만듭니다.

Uvicorn 기본 access log는 URL 쿼리를 포함하므로 `make dev-api`, Python 실행 진입점,
Dockerfile에 비활성 옵션을 적용했습니다. 앱 초기화에서도 해당 logger를 끕니다.
새 HTTP 로그는 INFO 이상을 항상 남깁니다. 기존 `LOG_LEVEL` 값으로 요청 로그의 원문
수집을 켜거나 필드 범위를 바꾸는 기능은 없습니다. 공급자 어댑터의 기존 전송 로그 차단도 유지합니다.

## 검증과 남은 범위

2026-09-16 `UV_OFFLINE=1 make check`: 백엔드 **620개**, 프론트엔드 **150개** 테스트와
Ruff·TypeScript·웹/백엔드 빌드가 통과했습니다.
`git diff --check`와 추적·추가 대상 138개 파일의 비밀정보 검사를 통과했으며 발견 0건입니다.
실제 `.env`는 변경하지 않았고 Git 제외 상태를 유지합니다.

자동 테스트는 환경 파일·실제 네트워크를 차단합니다. 새 검증은 ID/헤더/성공 본문의 일치,
접근 거절·422·429·503·500 분류, 원문 비노출, 동시 동기 계획 12건과 같은 자료를 공유하는
조회 6건의 ID 독립성, 취소·전송 중단, 오류 번호 교체·초기화·늦은 응답 무시를 포함합니다.
로컬 브라우저에서는 비활성 오류의 문의 번호와 실제 서버 로그 일치, 모의 자료 복구와
조건 승인·검토를 확인했습니다. 실제 외부 API 호출과 `.env` 변경은 없었습니다.

이 로그는 HTTP 경계 안의 정보만 제공합니다. 공급자별 상세 span·토큰/요금 집계,
로그 보관/접근 권한·분산 추적·통계/알림은 구현하지 않았습니다. 프로세스 시작 실패와
lifespan 오류, 프록시/플랫폼 로그는 이 처리 경계 밖입니다. 기관 stage에서 Cloud Logging의
보관·IAM·플랫폼 URL 로그 정책을 별도로 확인해야 합니다.

[읽기 전용 실습 운영 상태 화면](OPERATIONS_STATUS.md)도 완료했습니다. `/api/v1/operations`는
허용 경로 분류에 포함하며 상태 응답 본문이나 설정 값은 로그에 남기지 않습니다.
다음 최소 기능은 기관 stage 배포 준비입니다. 기관 Secret Manager·
Cloud Run stage 배포, 30명 부하 시험과 장애 리허설은 이후 범위입니다.

## 행사 스트림 오류 (2026-09-30)

`/api/v1/event/{plan|execute|general}/stream`과 `/api/v1/event/queue`도 고정 경로로
분류한다. 스트림 시작 후 실패는 HTTP 200에 종료 `error` 이벤트를 보내므로, 운영 집계는
HTTP 상태 외에 `jsonPayload.error_code`를 함께 확인해야 한다. `queue_timeout`,
`request_timeout`, `planner_billing` 등은 요청 ID와 함께 기록하고 원문·질문·키는 남기지
않는다. 근거를 보존한 브리핑 생성 실패는 성공 응답 안의 `brief.status`로 별도 집계한다.
[행사 대기·스트림 계약](EVENT_QUEUE.md)을 참고한다.
