# ADR 0022 — 81명 행사 접수와 처리량 보강

- 결정일: 2026-10-06
- 상태: 사용자 승인, 구현·처리량 검증 완료 (모델 품질 실패는 별도 기록)
- 근거: 최종 참가자 81명. 사용자가 수정 계획의 개발·실제 검증·공개 반영을 승인했다.

AI Studio에서 platform-monitor / Gemini 3.8 Flash / Tier 2의 RPM 2,000,
입력 TPM 3,000,000, RPD 100,000을 확인했다. stage Secret의 키 소속 프로젝트를
값 출력 없이 확인했으며 같은 프로젝트다. 공급자 승인 한도와 앱 자체 보호 한도는 구분한다.

단일 프로세스·단일 Cloud Run 인스턴스를 유지한다. stage 앱은 접수 120개,
Gemini 분당120/동시16, 공공 API 분당30/동시2로 시작한다. 요청 누적 대기240초,
전체300초, Cloud Run HTTP 동시160/제한330초, 브라우저 제한360초를 적용한다.
실제 사전 준비 중 일반 응답1건의20초 초과를 확인해30초로 조정했다. 후보20명에서
E 브리핑4건이30초 무렵에 중단돼 모델 개별 HTTP 제한을60초로 조정하고 같은 단계를 다시 검증했다.
첫 시험 도구는 실패를 일반화해 기록했으므로 네 건의 정확한 예외 종류를 확정하지 않는다.
이후 도구는 실행 기록의 실패 종류를 보존한다.
앱 전체300초 제한과 자동 재요청 금지는 유지한다.
대기 순서는 공급자 FIFO 안의 앞선 요청 수이며 전체 참가자의 순번이나 완료 예상이 아니다.
화면의 제한 시간은 서버 진행 상태로 전달한다. 기본 개발/이전 API 설정은 유지한다.

81명·120개 접수와 취소/해제/공유 조회를 모의 전송으로 검사한다. 후보의 실제 시험은
5→20→40→81명으로 확대한다. Gemini 최대350회, 공공자료 최대50회에 비상용 준비를
포함한다. 모델/공급자 실패가 생기면 증원을 멈추고 원인을 검토한다. 모델 검증 실패는
HTTP200·큐완료와 별도로 집계하고 숨은 재시도는 하지 않는다. 95%가120초 안에 종료하고
81명 동시 접수가 거절되지 않는 것을 목표로 하며 기능·원문·운영 합격은 구분한다.

20명 재검증에서 지연 해소·C의 출력 검증 거부1건과 명시적 재승인 복구를 확인했다.
40명은 접수·근거40건 성공, 브리핑38건 성공/C2건 검증 거부다. 이 알려진 품질 실패는
안전한 거부와 고정 snapshot으로 복구할 수 있어, 검토한 경우만81명 부하 확대를 허용한다.
도구의 `--reviewed-model-failures`는 해당 실패를 지우지 않고 이후 단계만 계속한다.
`capacity_passed`와 `quality_passed`를 분리하고 공급자·접수·계획 오류는 확대를 멈춘다.

최종81명은 계획81/81, 근거81/81, 브리핑80/81, 일반81/81이다. 단계 p95는 각각
38.088/103.894/95.915초, 혼잡·공급자 오류0건으로 처리량 목표를 통과했다.
C1건의 `InvalidPlannerOutput`은 근거를 보존하고 안전하게 거부한 품질 실패다.
자동 재요청 없이 기록하며 사전 생성 결과 선택으로 진행을 복구할 수 있다.
같은 다섯 공식 원자료 조건을 공유하고 실제 모델을 호출한 시험이며81개 서로 다른 실시간
공공자료 조건·행사장 네트워크를 대신하지 않는다. A~C 실시간 표본은 KOSIS8회로 따로
대조해 값·계산표 일치를 확인했다. 전체 사용량은 Gemini349/350회, 공공자료8/50회다.
Cloud Monitoring 분당p99 샘플의 최대 CPU약14%/메모리약38%로 기존 자원을 유지한다.

A~E의 대표 질문마다 실제 승인 실행한 결과·일반 응답을 비상용 고정 snapshot으로
검토·보관한다. 원자료 버전·원래 조회/모델 생성 시각·질문·조건을 유지하고 저장된 결과임을
표시한다. 참가자 선택·재승인 없이 전환하지 않는다. 새 브리핑과 사전 생성 재생을 구분한다.

동시 실행 증원은120/16의 결과가 안정적일 때 최대180/20까지 별도로 실측한다.
CPU/메모리는 측정으로 필요성을 판단한다. 데이터베이스·영속 큐·인증·멀티에이전트·기사
발행·공급자 한도 자체 변경은 추가하지 않는다. 후보 검증 뒤 공개하고 기존 공개 리비전을
보존한다. 행사 직전 최소 인스턴스1 준비·종료 후0 복귀는 기존 명령으로 실행한다.
