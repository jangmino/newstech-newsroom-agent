# 10월 7일 행사 버전 — 구현 및 검증 기준

계약의 기준은 [ADR 0018](decisions/0018-event-release.md)이다. 아래 항목은 완료 증거를
남긴 뒤 체크한다. 기존 제한형 실습의 완료 기록을 행사 확장 완료로 간주하지 않는다.

## 완료 보고의 네 구분

1. 기능: 구현 및 자동 테스트 통과 여부.
2. 실제 원문 대조: 공급자 API 응답 확인과 원문 화면/본문 대조를 별도 기록.
3. 오류 대응: 실제 발생 오류와 모의 전송/명시적 연습으로 검증한 오류를 구분.
4. 행사 운영: 개인 stage 결과와 실제 행사장·운영 책임 인계의 미완료를 구분.

가상 fixture는 개발에서 유지하며 참가자는 실제 조회 또는 공식 저장 자료만 선택한다.
새 통계 주제, 없는 자료 조합의 추정, 기관 이전, 자사 파일럿 작성은 이 구현에 포함하지 않는다.

## 참가자 진행

1부는 예시 질문으로 승인·출처·계산·검토를 익히고, 2부는 같은 검증 도구에 자유 질문과
자연어 조건 수정을 사용한다. 질문 분석은 Gemini와 회사 목록 확인만 수행한다.
대상·지표·기간·비교·연령/회계 기준을 확인한 뒤 **이 조건으로 조회**를 눌러야 근거와
브리핑이 나타난다. 수정한 조건은 표시하며 결과의 조회 조건에 그대로 남긴다.

일반 모델 비교 버튼은 별도 실제 모델 호출이다. 같은 질문·조건·모델을 사용하되 공식
조회 결과나 웹 도구를 제공하지 않는다. 입력 지시·시각·도구 유무를 공개한다. 특정 챗봇
제품 전체의 우열을 평가하는 실험이 아니다. 사람이 확인한 사실 2개와 근거, 미확인 해석,
후속 질문 2개, 데스크 확인 사항, 검토 이유를 작성하고 AI 초안을 수정·다운로드한다.
새 질문·조건·재조회는 검토 상태를 초기화한다. 다운로드 전 브라우저를 닫으면 작업은 사라진다.

장애 때는 자료 선택을 **공식 저장 자료**로 바꾸고 사례를 고른 뒤 다시 승인한다.
저장된 실제 자료·모델 출력은 수집 당시 조건과 시각을 유지한다. 새 모델 호출이 아니다.
임의 조건을 저장 사례의 값에 끼워 맞추지 않는다. mock은 개발용 LegacyApp 및 기존
API 테스트에서만 유지하며 참가자 진입 경로에서는 선택할 수 없다.

## API 계약

공유 접근코드와 기존 요청 ID·한도·오류 처리를 그대로 사용한다.

| 경로 | 입력 | 출력/외부 호출 |
|---|---|---|
| GET `/api/v1/event/catalog` | 없음 | 지원 범위·저장 사례 조건만; 외부 호출 없음 |
| POST `/api/v1/event/plan` | question, previous_conditions?, revision? | 조건·제안·field_errors·회사 후보·trace; 모델 및 공식 회사 목록 |
| POST `/api/v1/event/execute` | question, conditions, approved:true, mode:live/snapshot, snapshot_id? | 승인 조건·facts·brief·coverage·caveats·trace·cache·시각 |
| POST `/api/v1/event/general` | execute와 동일 | text·model·instruction·tools·승인 조건·생성 시각 |

conditions는 tool, entities, company_codes, metrics, start, end, frequency,
comparison, comparison_period, statement_basis, amount_basis, age_range이다.
`approved`는 문자열/숫자가 아닌 JSON true만 허용한다. snapshot은 질문과 전체 조건이
저장 사례와 정확히 같아야 한다. 기존 `/api/v1/analyze`와 research 계약은 개발 회귀 및
기존 도구 호환성을 위해 유지한다. 새 프론트엔드 타입은 `eventTypes.ts`이다.

공시는 회사당 목록 최대 3페이지·본문 최대 6건을 확인하고 초과/본문 실패를 부분 확인으로
표시한다. 본문은 최대 12,000자 발췌이며 전체 공시 검토가 아니다. 재무는 각 보고서의 당기
값을 사용하고, 연속 연간 보고서의 전기 비교값 재작성·계정 변경을 발견하면 증감 계산을
중단한다. 4분기는 연간−3분기 누적 차감이며 서로 다른 보고서의 회계정책·정정 여부를
사람이 대조해야 한다. 시도 순위는 중복 없는 기존 17개 시도 코드로 비교하며 새 통합 코드와
하위 지역을 합산하지 않는다. 카탈로그 제공 종료 시점은 2026-09-18 확인본으로 고정했다.

## 운영 예산

한 참가자의 계획 1회 + 승인 후 브리핑 1회 + 일반 응답 1회는 Gemini 최대 3회다.
자연어 수정·재승인은 각각 추가 1회이며 자동 재시도는 없다. 30명이 한 번씩 진행하면
기본 90회, 수정·재승인을 모두 한 번씩 하면 최대 150회다. 기존 Gemini 분당 30회/
동시 8개, 공공자료 공급자별 분당 30회/동시 2개, 1시간·64개 캐시를 유지한다.
계획·승인·비교를 단계별로 분산해 안내하고 429 때 연타하지 않는다. 저장 자료 재생은
외부 호출 0회다. 개인 stage 검증은 실제 참석자 30명·행사장 네트워크 검증과 구별한다.

행사 Gemini 3 모델은 양쪽 비교 응답과 계획에 동일한 LOW 추론 설정을 사용한다. 생각 내용은 노출하지 않는다. 실제 슬롯의 인용 연결은 코드가 보완하며 미등록 근거·직접 생성 숫자는 거부한다. [검증 기록](EVENT_VALIDATION.md)을 함께 확인한다.


## 진행자 점검 순서

1. 입장 후 운영 상태를 확인한다. 예시 질문 분석 후 승인 전 수치가 없음을 함께 확인한다.
2. 제안된 대상·기간·연령/회계 기준의 의미를 묻고 한 조건을 수정한 뒤 승인한다.
3. 일반 응답을 별도 생성하고 구체성, 출처 추적, 확인 불가능한 해석을 비교한다.
4. 근거의 공식 원문을 열어 단위·기간·계정을 대조한다. 조건을 바꿔 재승인하고 결과 차이를 설명한다.
5. 사람 검토 기록을 작성하고 AI 문장을 수정한다. 실습 완료와 기사 사용 승인이 다름을 확인한다.
6. 2부에서는 공시·재무·고용 중 자유 질문을 받고, 자료가 없는 조합은 안내 자체를 검토한다.
7. 장애 시 운영자는 호출을 잠시 멈추도록 안내한다. 참가자가 공식 저장 사례를 선택하고
   재승인한 뒤 원래 시각과 동일 조건의 사전 생성 응답으로 계속한다.
8. 종료 전에 검토 기록을 내려받는다. 창을 닫기 전 파일이 실제 저장되었는지 참가자가 확인한다.

월간 시도 고용률·15~34세·공시와 고용의 인과관계 결합은 지원 불가 설명을 확인하는 사례다.
이를 다른 지표/연령으로 몰래 대체해 성공 사례로 시연하지 않는다. 기관 이전과 현장 리허설은
최종 인계 시 확인하며 자사 파일럿 작성 활동은 포함하지 않는다.


운영자가 다시 실제 호출을 검증하려면 다음 명령을 사용한다. 기본 4개 흐름이며 `--users 30`은
Gemini 최대 90회다. 접근코드 파일은 Git에 넣지 않고 결과 경로도 `.cache/`에 둔다.

```bash
apps/api/.venv/bin/python scripts/event_rehearsal.py \
  --origin https://YOUR-STAGE.run.app \
  --access-code-file .cache/stage-workshop-code.txt \
  --output .cache/event-rehearsal-NEW.json \
  --users 30 --interval 20 --execute-live
```

HTTP 실패나 계약 불일치 때 중단한다. 브리핑 실패는 근거 보존과 오류 문구를 확인해
기록하며, 최종 브리핑 성공률이 90% 미만이면 리허설 불합격으로 판정한다. 90%는 이번
리허설의 내부 기준이며 행사 당일 무중단을 보장하지 않는다. 실패 시 참가자의 재승인 또는
공식 저장 자료 선택이 필요하다.
