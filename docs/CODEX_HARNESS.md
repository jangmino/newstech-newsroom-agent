# Codex 개발 하네스

이 문서는 VS Code의 Codex 확장과 대화하면서 저장소를 점진적으로 개발하기 위한 작업 규칙입니다.

## 1. 세션 시작

VS Code에서 `/Users/jangmin/work/newstech-newsroom-agent` 폴더 자체를 엽니다. 하위 폴더만 열지 않습니다.

새 Codex 대화의 첫 요청 예시:

```text
AGENTS.md와 docs/PRODUCT_BRIEF.md, docs/ARCHITECTURE.md,
docs/CODEX_HARNESS.md를 읽고 현재 구현 상태를 설명해줘.
파일은 아직 수정하지 말고, 다음으로 개발할 가장 작은 기능 한 개를 제안해줘.
```

공식 OpenAI 문서에 따르면 Codex는 Git 루트부터 현재 작업 폴더까지 `AGENTS.md`를 읽습니다. 작업을 하위 폴더에서 시작하더라도 루트 지침이 적용되도록 저장소 루트를 VS Code 작업공간으로 사용합니다.

## 2. 한 번에 하나의 제품 단위

다음 순서로 구현합니다.

1. M0: mock 흐름과 화면 계약
2. M1: 질문 조건 편집·승인 UI
3. M1: 일반 응답 예시와 근거 기반 mock 브리핑 비교
4. M2 준비: 작은 mock 수치 자료와 결정론적 계산·검증 기초
5. M1: 사람 검토 상태·조건 변경에 따른 결과 비교·오류 체험 시나리오
6. M2: Gemini 질문 구조화
7. M2: OpenDART 실습 시나리오
8. M2: KOSIS 실습 시나리오와 실제 자료의 단위·누락값 검증
9. M3: 캐시·속도 제한·snapshot fallback
10. M3: 접근코드와 운영 화면
11. M3: Cloud Run stage 배포
12. M3: 30명 부하 시험과 리허설

로드맵의 마일스톤은 기능 범위이고, 위 목록은 구현 순서입니다. M1 비교 화면을 먼저
확인한 뒤 M2의 계산 기초를 mock 자료로 구현하여 M1의 결과 비교에 사용합니다.
실제 공급자 연결과 검증된 공식 원자료 fixture는 그 이후에 진행합니다.

응답 비교의 일반 응답은 미리 작성한 실습 예시임을 명시합니다. 실제 모델의 출력이나
성능 평가로 소개하지 않습니다. 조건 승인 전에는 두 응답을 표시하지 않으며,
근거 기반 mock 응답은 공식 자료를 조회한 것으로 표현하지 않습니다. 청년 고용 실습의
결정론적 계산은 가상 지역·가상 숫자임을 원자료 표와 브리핑에 명시합니다.
숫자가 없는 기업 실적 mock은 계산이 이뤄진 것으로 표현하지 않습니다.

현재 1~5번을 mock 범위에서 완료했습니다. 계산 기초의 범위와 규칙은
[ADR 0003](decisions/0003-synthetic-mock-calculations.md)에 기록합니다.
5번은 [사람 검토 상태](REVIEW_FLOW.md), [조건 변경 전후 비교](CONDITION_COMPARISON.md),
[오류·모호성 실습 안내](WORKSHOP_SCENARIOS.md)로 구성합니다. 체크 상태는 현재 결과의
화면에만 유지하고, 조건 변경·재조회 시 무효화합니다. 실습 항목 확인을 실제 자료 검증
완료나 기사 사용 승인으로 표현하지 않습니다. API의 `review_required`는 유지합니다.
조건 비교는 같은 질문의 직전 성공 결과와 이번 결과로 한정합니다. 편집·조회·오류 중에는
결과를 숨기고, 질문 변경·재분석 시 비교 기준도 초기화합니다. 단위나 조건이 다른 값의
차이를 새 수치로 만들지 않습니다. 실습 안내는 기존 질문·자료·검증 규칙을 사용하며,
예시 조건 적용과 조회 승인을 분리합니다. 다른 기간 선택을 원래 누락값의 해결로 표현하지 않습니다.

6번의 준비 단계인 **질문 구조화 어댑터와 계약 검증(mock)**을 완료했습니다.
[질문 구조화 계약](QUESTION_PLANNING.md)에 따라 잘못된 출력은 중단하고,
불확실하거나 지원하지 않는 조건은 참가자가 확인하도록 비웁니다. 승인 후에는
해석기를 다시 호출하지 않습니다. 기본 해석과 자료 조회는 mock입니다.

**Gemini 질문 해석 어댑터 연결 코드와 모의 전송 검증**도 완료했습니다.
[ADR 0004](decisions/0004-gemini-planning-with-mock-evidence.md)에 따라 실제 모델 선택과
서버 활성화 설정을 분리합니다. 실제 모델을 사용해도 공공데이터는 mock을 유지하며
해석 방식과 자료 모드를 따로 표시합니다. 자동 재시도·자동 mock 대체는 없습니다.

**기존 두 질문의 소규모 Gemini 실제 해석 확인**도 완료했습니다. 2026-09-16 로컬
API 키 인증으로 네 질문을 한 번씩 확인했으며, 모호성·명시 조건·수정 후 승인 흐름이
기대대로 동작했습니다. 키 값이나 `.env` 내용은 직접 조회·출력하지 않았고 백엔드만
기존 설정을 사용했습니다. 자동 테스트는 계속 모의 전송만 사용합니다.
절차·결과·한계는 [실제 해석 확인 기록](GEMINI_SMOKE_TEST.md)에 있습니다.

7번 **OpenDART 승인 후 실제 조회 흐름**을 완료했습니다. 삼성전자 2022·2024년 연간
연결 매출액을 실제 API와 공시 원문으로 대조했고, 조건 승인 → 조회 → 결정론적 증감
계산 → 근거·브리핑·사람 검토까지 연결했습니다. [조회 계약](OPENDART_REVENUE.md),
[확인 기록](OPENDART_SMOKE_TEST.md), [ADR 0006](decisions/0006-opendart-approved-live-flow.md)을
따릅니다. 비교 기준은 증감 폭/률이며 다른 기업·지표·연도·별도·분기는 live 미지원입니다.
일반 응답은 계속 고정 모의 예시이며 브리핑 모델 호출도 없습니다.

8번의 준비 단계인 **KOSIS 청년 고용의 공식 통계표·차원·단위 계약 확인**을 완료했습니다.
실제 API 6회로 15~29세 고용률의 17개 시도·2020~2024년 85개 셀과 메타데이터를 확인하고,
공개 발췌·순수 정규화·오프라인 테스트를 추가했습니다. [자료 계약](KOSIS_EMPLOYMENT.md)과
[ADR 0007](decisions/0007-kosis-youth-employment-contract.md)을 따릅니다. 15~34세와 취업자 수는
이 표의 확인된 직접 조회 범위에 없으므로 임의로 대체하지 않습니다.

8번 **KOSIS 승인 후 실제 조회 흐름**도 완료했습니다. `KOSIS_ENABLED`를 별도로 검사하고
승인 한 번에 최대 85개 셀을 한 번 조회합니다. 시도별 증감 폭/률·순위·연간 원자료·
조회 시각·최종수정일·원표 링크와 사람 검토를 연결했습니다. 실제 UI 조회 2회와 공식
통계표의 시작·종료 값 34개 대조를 마쳤습니다. [ADR 0008](decisions/0008-kosis-approved-live-flow.md),
[실제 확인 기록](KOSIS_SMOKE_TEST.md)을 따릅니다. 기존 mock 선택지는 유지합니다.

현재는 **기존 두 실습 질문의 한정된 M2 연결을 마치고 M3 운영 준비를 진행 중**입니다.
9번의 첫 단위인 **공공자료의 프로세스 내부 캐시와 동일 조회 요청 합치기**를 완료했습니다.
원자료만 기본 1시간 재사용하고 참가자의 조건 승인을 유지하며 사용 여부·원래 조회 시각·
기한을 표시합니다. 승인 전 조회, 실패 결과 캐시, 숨은 snapshot 대체는 없습니다.
비교 기준만 달라지면 같은 원자료로 계산·브리핑·요청 ID를 새로 만들고 검토를 초기화합니다.
[ADR 0009](decisions/0009-process-public-data-cache.md), [캐시 계약·검증](PUBLIC_DATA_CACHE.md)을 따릅니다.

9번의 두 번째 단위인 **공공자료 호출·동시 실행 제한**도 완료했습니다. 자료원마다
최근 60초 HTTP 시작 30회·동시 2회를 기본값으로 적용합니다. 캐시 hit와 동일 조회를
기다리는 참가자는 추가 한도를 쓰지 않습니다. OpenDART 두 연도는 각각 1회이며 두 번째
거절 시 부분 결과를 버립니다. 한국어 429·예상 대기 안내와 명시적 재승인을 제공하고
자동 재시도·자료 대체는 하지 않습니다. [ADR 0010](decisions/0010-process-public-data-limits.md),
[호출 제한 계약·검증](PUBLIC_DATA_LIMITS.md)을 따릅니다. 행사 전체·여러 인스턴스 정책은 별도입니다.

9번의 세 번째 단위인 **명시적 snapshot fallback**도 완료했습니다. 기존 공개 발췌를
버전과 해시를 고정한 백엔드 패키지 자료로 옮겼습니다. 참가자는 처음부터 공식 저장 자료를
선택하거나 실제 조회 오류 뒤 기존 편집 조건을 유지해 전환합니다. 안내 확인·별도 승인
전에는 근거·브리핑을 표시하지 않습니다. 원래 조회 시각·지원 범위·개정 미반영을 명시하며
live 실패를 숨기거나 mock을 공식 자료로 표현하지 않습니다. [ADR 0011](decisions/0011-explicit-public-data-snapshot.md),
[저장 자료 계약·확인 방법](SNAPSHOT_FALLBACK.md)을 따릅니다.

10번의 첫 단위인 **행사용 접근코드**를 완료했습니다. 계정·DB 없이 공유 코드로 모든
실습 API와 문서 경로를 보호합니다. local/test의 빈 코드만 제한 없이 사용하며 stage/event의
미설정·잘못된 코드는 접근을 막습니다. 참가자는 입장 뒤 별도로 조건을 승인하고, 나가기·
재입장 필요 시 결과·비교·검토를 초기화합니다. 코드는 탭 메모리에만 유지하고 헤더로 전송하며
원문을 로그에 남기지 않습니다. [ADR 0012](decisions/0012-shared-workshop-access-code.md),
[접근 계약·설정·검증](WORKSHOP_ACCESS.md)을 따릅니다.

10번의 두 번째 단위인 **요청 ID와 구조화 로그**도 완료했습니다. 응답 헤더·성공 본문·
서버 JSON 로그에 같은 UUID를 사용하고 오류 화면에 문의 번호를 표시합니다. 허용된 경로
분류·상태·처리 시간·실패 코드만 기록하며 질문·코드·키·쿼리·예외 원문은 남기지 않습니다.
기본 서버 access log를 끄고 동시 요청·캐시 공유에서도 ID를 구분합니다.
[ADR 0013](decisions/0013-request-id-and-safe-logs.md), [로그 계약·확인 방법](REQUEST_LOGGING.md)을 따릅니다.

10번의 세 번째 단위인 **읽기 전용 실습 운영 상태 화면**도 완료했습니다. 실제 공급자를
호출하지 않고 설정상 허용 여부·저장 파일 사용 가능 여부·캐시/호출 제한 설정과 프로세스
적용 범위를 확인합니다. 현재 실습 결과와 검토를 유지하며 수동으로 갱신합니다.
운영 제어·별도 관리자 계정·키 값 노출은 없습니다. [ADR 0014](decisions/0014-read-only-operations-status.md),
[운영 상태 계약·확인 방법](OPERATIONS_STATUS.md)을 따릅니다.

11번은 사용자 요청에 따라 **개인 GCP의 임시 stage**로 먼저 진행합니다. 기관 계정을 받기
전까지 전용 개인 프로젝트에서 단일 Cloud Run·Secret Manager·비용 알림을 구성합니다.
서울 리전·1 CPU/512 MiB·최소 0/리비전 최대 1·동시 8, 첫 배포 mock/저장 자료·월 1만원
알림·공개 URL과 공유 접근코드의 범위로 사용자 승인을 받았습니다. 동일 범위의 생성·빌드·
배포·검증마다 다시 승인받지 않습니다. [ADR 0015](decisions/0015-temporary-personal-stage.md),
[배포 절차와 기관 교체](STAGE_DEPLOYMENT.md)를 따릅니다. 계정·프로젝트 이름은 Git 제외
로컬 설정에만 두고, Secret은 숫자 버전·이미지는 digest로 고정합니다.

기관 계정을 받으면 기관 소유 자원·키·접근코드로 새로 배포하고 참가자 URL을 교체합니다.
개인 Secret 값을 기관에 복사하지 않습니다. 기관 stage·행사 조건의 부하 확인·리허설과 넓은
Gemini 품질 검증은 아직 남아 있습니다. 실제 공급자 live 활성화는 별도 후속 검증입니다.

11번의 **개인 임시 stage 배포와 소규모 확인**을 완료했습니다. Cloud Build 이미지와
Secret 버전을 고정하고, 공개 입장 화면·코드 보호·mock/저장 자료의 승인 실행·요청 로그를
확인했습니다. [배포 확인 기록](STAGE_SMOKE_TEST.md)을 따릅니다.

12번의 첫 단위인 **stage 30명 단기 API 부하 시험(mock/저장 자료)**을 완료했습니다.
1→5→15→30명, 총 766개 요청의 승인·조건 수정·검토 상태·응답 시간 기준을 통과했습니다.
도구와 오프라인 검사를 추가했고 실제 공급자 호출이나 stage 설정 변경은 없었습니다.
[부하 시험 범위·결과](STAGE_LOAD_TEST.md)를 따릅니다. 약 3초의 30명 구간을 지속 부하·
실제 공급자 성능·행사장 브라우저 검증으로 표현하지 않습니다. 다음 최소 단위는
**장애·공식 저장 자료 전환 리허설**이며 live 연결·행사 조건의 부하 확인은 남아 있습니다.

사용자가 OpenDART처럼 한 공급자의 완성을 요청하면 원문 대조·어댑터·승인 UI·테스트·
문서를 하나의 승인 범위로 연속 진행할 수 있습니다. 내부적으로 검증과 Git 체크포인트를
나누며 매 단계마다 다시 승인을 요청하지 않습니다. 기존 질문의 의미 변경, 해결할 수
없는 접근 권한 문제, 승인 범위 밖 공급자·운영 기능 추가가 필요하면 사용자에게 알립니다.

## 3. 작업 요청 템플릿

### 기능 구현

```text
[사용자 결과] 참가자가 질문 해석 조건을 직접 수정할 수 있게 해줘.
[범위] apps/web의 조건 패널과 필요한 API 계약만 수정해줘.
[제외] 실제 OpenDART/KOSIS 호출과 배포는 하지 마.
[검증] 관련 테스트와 typecheck를 실행해줘.
[문서] 계약이나 실행 방법이 바뀌면 관련 문서도 고쳐줘.
```

### API 연동

```text
OpenDART의 회사 개요 조회를 구현해줘.
공식 개발가이드를 먼저 확인하고 provider adapter 안에만 구현해.
실제 키나 네트워크를 사용하는 테스트는 만들지 말고 MockTransport로 검증해.
오류 코드, 타임아웃, 로그의 키 마스킹을 포함해줘.
```

### 리뷰

```text
현재 diff를 뉴스룸 신뢰성, 비밀정보 노출, API 장애 처리,
30명 동시 사용이라는 네 관점에서 검토해줘.
수정은 하지 말고 심각도와 근거를 먼저 알려줘.
```

## 4. 작업 전후 체크포인트

작업 전:

```bash
git status --short
make doctor
```

작업 후:

```bash
make check
git diff --check
git status --short
```

검토 UI의 좁은 검증은 `make test-web`입니다. Vitest·React Testing Library로 모의 응답을
사용해 체크·해제·승인 전 숨김·결과 무효화를 검사합니다. 테스트 실행기는 dotenv 파일을
읽지 않도록 Vite의 인라인 `envFile: false` 옵션을 사용합니다. 새 동작을 추가할 때도
실제 공급자 요청이나 브라우저 저장소에 의존하지 않습니다.

의미 있는 기능 단위가 끝나면 Git 커밋을 만듭니다. 개인 키나 `.env`가 스테이징되지 않았는지 반드시 확인합니다.

## 5. 외부 API 안전 규칙

- 실제 호출이 필요할 때만 `LIVE_API_ENABLED=true`로 바꿉니다.
- 자동 테스트는 항상 mock transport 또는 fixture를 사용합니다.
- 개인 공급자 키는 로컬 `.env`에만 둡니다. 임시 개인 stage의 첫 배포는 키 없이 mock/저장 자료로 확인합니다.
- 임시 stage의 접근코드는 개인 프로젝트 Secret Manager에 둡니다. 기관 전환 시 기관 소유 Secret과 새 접근코드를 사용합니다.
- API 호출 수를 늘리는 변경은 예상 호출량을 먼저 계산합니다.
- fallback 자료는 실시간 자료처럼 표시하지 않습니다.
