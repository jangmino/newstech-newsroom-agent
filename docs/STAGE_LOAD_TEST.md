# Stage 30명 동시 사용 시험

## 목적과 범위

M3의 개인 임시 stage에서 30명이 질문 조건을 확인·승인하고 다시 편집하는 API 흐름을
검증합니다. 정상 예상 인원에 대한 **부하 시험**이며, 장애가 날 때까지 인원을 늘리는
스트레스 시험은 아닙니다. 실제 공급자 호출·설정 변경·재배포 없이 기존 mock·공식 저장
자료만 사용합니다. 새 서비스·DB·인증·의존성을 추가하지 않습니다.

이는 HTTP 수준의 수동 운영 검증입니다. 30개 실제 브라우저의 렌더링·검토 체크 조작,
행사장 와이파이, 장시간 안정성, scale-to-zero 이후 동시 입장, Gemini·공공자료 live 지연과
공급자 한도·캐시 효과는 검증하지 않습니다. 첫 health 요청은 준비 시간에 포함하며 본
부하의 지연 통계와 분리합니다. 앱과 Cloud Run 설정은 기존 배포 그대로 사용합니다.

## 시나리오와 요청 예산

`scripts/stage_load.py`가 **1 → 5 → 15 → 30명** 순서로 실행합니다. 단계별로 모든 참가자
작업을 동시에 시작하고, 한 참가자는 요청을 순서대로 보냅니다. 참가자별 순서를 회전하여
mock/snapshot × KOSIS/OpenDART 네 조합이 섞이게 합니다.

1. 공개 입장 상태 확인 → 공유 코드로 입장.
2. 모의 규칙으로 질문 계획 → 근거·브리핑이 없고 조건이 명확한지 확인.
3. 조건 확인을 대신하는 0.25초 대기 → 명시적 승인 → 결과·조회 조건·출처 정보 확인.
4. 비교 기준을 증감 폭에서 증감률로 수정 → 0.25초 대기 → 재승인 → 변경된 조건 확인.
5. 네 조합 모두 반복. 승인 결과는 계속 `review_required`여야 합니다.

대기를 짧게 압축하므로 사람의 실제 읽기 속도를 재현하지 않습니다. 하나의 HTTPX 연결
풀에서 HTTP/1.1 연결을 최대 30개 사용합니다. 클라이언트 동시 진행 수는 서버에서 동시에
처리한 수와 다릅니다. 설정의 Cloud Run 동시 요청 8을 변경하지 않습니다.

총 204개 시나리오 흐름·408개 승인 조회입니다. 외부 공급자 요청은 0회입니다.
Cloud Run/로그 요청 비용은 발생할 수 있지만 프로젝트·인스턴스·과금 설정은 변경하지 않습니다.
자동 재시도·리다이렉트·환경 프록시는 사용하지 않습니다. 단계당 총 120초, 요청당 총 15초로
제한합니다. 최대 30명·네 단계만 허용하며 실패하면 남은 작업을 취소하고 증원을 중단합니다.

각 단계 전에 stage·mock 기본값·live off·세 공급자 disabled·저장 자료 available을 확인합니다.
공유 코드 없는 운영 API는 401, 네 조합의 승인 없는 실행은 422여야 합니다. 성공한 단계
뒤에도 공급자 비활성·저장 자료 상태를 재확인합니다. 401/422는 의도한 보호 동작으로
예상 밖 오류와 별도로 집계합니다. `external_calls_made=false`는 운영 상태 API 자체의
무호출 표시이며 서버 전체 외부 호출 횟수 측정치가 아닙니다.

## 사전에 정한 판정 기준

- 모든 참가자의 네 흐름과 재승인이 완료되어야 합니다.
- 예상 밖 HTTP 상태·네트워크 오류·시간 초과·계약 오류는 0건이어야 합니다.
- 승인 전 근거·브리핑 비노출, 승인 조건과 최종 조회 조건·필터 일치, snapshot 버전·
  원래 시각 유지, 사람 검토 상태 유지, 요청 헤더/본문 ID 일치·단계 내 중복 없음이 필요합니다.
- 각 단계의 계획·승인 조회 요청 각각 **p95 ≤ 2,000ms**여야 합니다. p95는 오름차순
  `ceil(0.95 × 요청 수)`번째 값이며 클라이언트 왕복 시간입니다. 장기 서비스 SLO나
  실제 공급자 성능 기준이 아닌 이번 mock/저장 자료 시험의 잠정 목표입니다.

## 실행

자동 테스트는 ASGITransport·MockTransport와 가상 코드만 사용합니다. `.env`와 실제
네트워크는 기존 pytest 보호 장치가 차단합니다. `make check`는 클라우드 시험을 실행하지
않으며 배포·부하 스크립트의 Ruff 검사도 포함합니다.

수동 stage 시험은 저장소 루트에서 기존 Python 환경을 사용합니다. URL은 승인된 실제
stage origin으로 바꾸고, 보고서는 아직 없는 Git 제외 경로를 지정합니다.

```bash
apps/api/.venv/bin/python scripts/stage_load.py \
  --base-url https://YOUR-STAGE.run.app \
  --access-code-file .cache/stage-workshop-code.txt \
  --report .cache/stage-load-result.json
```

접근코드 파일은 소유자만 읽는 권한이어야 합니다. 값은 메모리에서 요청 헤더로만 보내고
명령 인자·출력·보고서에 넣지 않습니다. 도구는 `.env`, GCP 자격증명, Secret Manager를
읽지 않습니다. URL의 계정·쿼리·경로·fragment를 거부하고 HTTPS origin만 받습니다.
보고서는 고정된 단계/요청 이름·횟수·상태·지연 통계·고정 실패 코드만 기록합니다.
원문 응답·질문·헤더·실제 코드·API 키·개인 프로젝트 주소는 저장하지 않습니다.
기존 보고서를 덮어쓰지 않으며 성공은 종료 코드 0, 시험 실패는 1, 실행 준비 오류는 2입니다.

HTTP 클라이언트는 기존 의존성을 재사용합니다. 연결 재사용과 타임아웃의 배경은
[HTTPX 비동기 사용](https://www.python-httpx.org/async/),
[HTTPX 타임아웃](https://www.python-httpx.org/advanced/timeouts/)을 참고합니다.
