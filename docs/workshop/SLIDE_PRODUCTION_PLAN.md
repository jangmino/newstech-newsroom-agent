## 전달할 중심 내용

참가자는 취재 질문을 공식 자료로 확인 가능한 조사 계획으로 바꾸고, 승인된 근거와 계산으로 작성한 브리핑을 검토한다. 강의의 최종 산출물은 사실 2개, 부족한 해석 1개, 후속 질문 2개, 데스크 확인 항목, 수정한 브리핑과 검토 기록이다. 기사 자동 작성·발행은 포함하지 않는다.

기술적 깊이는 세 수준으로 구성한다.

- **모든 참가자:** 승인 전후 경계, 공식 자료의 제공 범위, 일반 응답과 근거 브리핑의 입력 차이, 사람이 판단할 부분.
- **기술에 관심 있는 참가자:** React–FastAPI 역할, Gemini의 계획·설명 역할, 코드 계산과 출력 검증, Cloud Run 단일 배포.
- **개발·데이터·IT 담당자:** 실제 메시지 계약, 어댑터와 검증 사례, MCP·개발 도구·프레임워크의 차이, 취재 지식 관리와 권한·갱신 운영. 부록에서 설명한다.

## 이번 구성에서 추가한 교육 장치

- “어느 쪽이 더 좋은 문장인가?”와 “어느 문장을 원문으로 확인할 수 있는가?”를 따로 묻는다.
- UI의 화면 순서와 서버 실행 순서를 구분한다. 브리핑은 승인 실행 중 먼저 만들며, 일반 응답은 비교 버튼으로 별도 요청한다.
- `approved_conditions`는 우리가 만든 필드명임을 설명한다. 필드 이름이나 자료원 이름만으로 도구가 호출되지는 않는다.
- A–E 모두를 완주시키지 않는다. 짧게 소개한 뒤 조별 한 사례를 깊게 다룬다. 진행자는 C로 비교표를, D/E로 자료 준비와 해석의 경계를 설명한다.
- 확인된 수치 변화에서 원인을 자동 추론하지 않는 연습을 한다. 공식 자료라는 이유로 원문 대조와 사람 검토를 생략하지 않는다.

## PPTX 제작 완료 기준

1. 오후 일정의 각 구간 합계가 맞고, 16시 종료를 넘지 않는다.
2. 초안의 흰 배경·검정 제목·절제된 파랑·여백과 16:9 비율을 유지한다.
3. 다이어그램의 화살표와 승인 경계가 실제 코드와 일치한다. Gemini 직접 API 호출, 별도 프론트 서버, 모델에 API 키 전송 등 잘못된 구조를 그리지 않는다.
4. 본편에는 읽을 수 있는 짧은 코드 예시만 넣고, 전체 JSON·시스템 지시문은 부록이나 배포 자료로 보낸다.
5. 화면 캡처는 실제 앱에서 촬영하고, 자료 방식·조회 시각·검증 범위를 보존한다. 생성하지 않은 성공 응답을 합성하지 않는다.
6. D/E의 저장 원자료, A–C의 실제 조회, 고정 응답 재생을 같은 의미로 설명하지 않는다.
7. 모든 장을 렌더링해 글꼴·잘림·다이어그램 연결·표와 캡처의 가독성을 확인한다.
8. 출처는 발표자 노트와 배포용 참고 자료에 연결한다. 최신 모델명·서비스 버전·한도는 제작 시 재확인하고, 미확인 숫자를 단정하지 않는다.

## 진행 중 늦어질 때

시간이 부족하면 A–E의 상세 소개는 각 조가 원고를 읽게 하고, 부록 설명과 일반 응답의 두 번째 호출을 생략한다. **조건 승인, 근거 한 건의 원문 대조, 사람 검토 기록과 내려받기는 유지한다.** 대기·실패의 실제 행동 안내는 S17 및 X08을 따른다.
